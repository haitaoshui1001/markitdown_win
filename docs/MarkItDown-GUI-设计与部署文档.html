02需求与关键决策

原始需求三句话：可执行软件、单个与批量都能转、参数都能在界面配置。落地时做了四个取舍，每个都有明确代价。

决策选择理由承担的代价
打包形态目录版 onedir启动不解压临时目录、冷启动 1 秒级；onedir 是 PyInstaller 兼容性最好的路径，magika 的 onnx 模型能按原目录结构就位分发要带整个文件夹，285 MB，不能只发一个 exe
参数范围全部暴露、默认关闭云端与 LLM 参数需要自备密钥，默认关闭可保证「装好就能离线用」；同时不阉割高级能力界面项多，需要分组 + 滚动 + 配置预设来压复杂度
构建环境独立 venv不污染 Anaconda base，依赖集合可复现，打包体积只含实际需要的包换机重建环境需按第 14 节命令重装
并发单位线程 × N，每线程一个引擎实例markitdown 的耗时在 IO 与解析，线程比进程轻；但 magika 模型初始化极贵，必须按线程复用而非按文件UI 锁定期不能改参数；GIL 下 CPU 密集格式加速比不到线性

明确不做的事

  • 不做 onefile 单文件版：每次启动解压 266 MB，冷启动 5～15 秒，且 magika 模型路径需要额外 hook，收益不抵风险。
  • 不做老版 .doc / .ppt / .rtf 支持：markitdown 离线不含这些转换器，界面对应扩展名直接不收录，避免「加了文件却必然失败」。
  • 不做命令行模式：验证走 --selftest，只用于打包产物自检，不是对外功能。

为什么引擎层不依赖 Qt

这是整套设计里最值钱的一条约束。它带来三个直接收益：

  1. 可测：scripts/verify_engine.py 26 项检查全部不需要起界面，跑一次 3 秒；如果转换逻辑混在槽函数里，就只能靠人肉点界面。
  2. 可换壳：将来要做 CLI、右键菜单、开机服务，直接复用 run_batch，不必拆 Qt。
  3. 打包可分段验证：--selftest 走的就是引擎层，能在 windowed exe 没有 stdout 的情况下单独证明「依赖装全了」，把「引擎坏」和「界面坏」区分开。

04转换流水线

一次「转换队列（批量）」点击背后是五步，前三步全部在 GUI 线程单线程完成，只有最后一步进线程池。

枚举阶段的四条过滤规则

collect_sources() 对每个候选路径依次判断，顺序固定：

  1. 必须是文件，目录本身不进队列。
  2. 隐藏项：路径任一段以 . 开头则丢弃，除非勾选「包含隐藏文件/目录」。
  3. 扩展名白名单：勾选「只收录可识别的扩展名」时，只保留 46 种离线可识别扩展名；取消勾选则全量收录，交给 markitdown 自己判断。
  4. 不吃自己的产出：输出后缀（默认 .md）且落在输出目录或扫描根目录内的文件被排除——否则第二轮批量会把上一轮生成的 Markdown 再转一遍，形成自我增殖。

同一文件既从「添加文件」进来、又被某个「添加文件夹」覆盖时，按 resolve() 后的真实路径去重，只转一次。

转不出正文时：宁可没有文件，也不要一个空文件

markitdown 对「无法提取文字」有三条不同的返回路径，早期版本把它们混在一起处理，结果是用户拿到一堆 0 字节的 .md，看起来像转换成功。现在三条路径各自收口：

路径触发条件处理状态
转换成功但正文为空ImageConverter 只从 exiftool 取元数据；无元数据、又没启用 LLM 时返回空串不写文件，target = None，chars = 0无内容
UnsupportedFormatException.gif / .bmp / .tiff / .webp 等不在转换器接受范围内沿用异常，但翻成中文一句话；原始信息留在 detail失败
FileConversionException（音频）AudioConverter 固定要连云端语音端点进转换前先预检拦截，见下无内容
为什么要预检（preflight_skip()）：音频转换器在没有配置任何云端能力时并不会快速失败，而是去拨一个固定端点，实测 WinError 10060 要等约 42 秒 TCP 连接超时。批量里有几段录音就会白等几分钟，而且进度条看着像卡死。所以 llm_enabled / use_cu / use_docintel 全关时，音频在调用转换之前就被判为「无内容」并给出可行动说明；一旦用户勾了任一云端能力，预检立即放行，交回真实转换路径。

文案由 no_content_hint() 与 failure_hint() 两个纯函数生成，都返回 (一句话, 补充说明)：一句话进「说明」列，补充说明进悬停提示与运行日志，并带上下一步动作——「需要正文请在右侧勾选『用多模态 LLM 给图片写描述』，或启用 Azure Content Understanding 后重转」。启用云端后仍为空时，提示会改成「请检查模型名、Endpoint 与密钥是否有效」，不会把两种情形混成一句。

「无内容」与「失败」都不会在「输出文件」列留下路径，因此双击不会打开一个不存在的文件；两类状态都保留在「转换队列（批量）」的重跑筛选里，改完云端参数可以直接再转一次。默认扩展名白名单仍然收录 .gif/.bmp/.tiff/.webp——用户本来就会往里拖，把它们排除掉只会让人以为程序"没反应"，现在的做法是允许添加、然后把不支持说清楚。

单文件快速转换走的是同一条路

「快速转换单个文件…」不经过枚举和路径规划：选源文件 → 预填默认输出路径 → 允许改名/换目录 → 以 conflict="overwrite" 强制覆盖语义提交单个 JobItem。这样既复用线程与信号机制，又不会因为「重名时=跳过」的队列设置让用户误以为转换失败。

单文件没有表格行可以承载反馈，所以结束时多做一步：_announce_quick_single() 在没有产出 Markdown 时直接弹窗告知「未能生成 Markdown」并附上原因与下一步；批量则只在日志里汇总一次（N 个文件没有可提取的正文，未生成 Markdown：…），不打断操作。

05并发模型

一个 GUI 线程 + N 个 worker 线程，跨线程只通过信号传递，worker 从不直接碰控件。

三个容易踩的坑，以及代码里的对应处理

坑现象处理位置
引擎实例按文件创建每个文件都要重载 magika 的 onnx 模型，批量比单线程还慢run_batch() 接收整个 chunk，进入循环前 new_markitdown() 一次engine.py:428
按文件提交线程池线程池每个任务各自初始化引擎，等于把上一个坑放大先 _partition 交错切片，一个 chunk 一个 BatchTaskui_main.py:626
第一个 chunk 完成就解锁界面显示可操作，但后台还在跑，用户改参数或关窗chunk_finished 信号 + active_chunks 计数，归零才解锁ui_main.py:711
GUI 回调里写 item.status批量跑得快时，item_started 的队列信号晚于 worker 的 on_item，槽函数把已经写好的「完成」改回「转换中」，行永远停在转换中（真实复现：3 行卡住）状态只由工作线程写；转换中 在 emit on_start 之前于 worker 内赋值，_on_item_started 降级为纯重画。回归里用一条断言钉住：_on_item_started() 后状态必须仍是「完成」engine.py run_batch / ui_main.py:_on_item_started

交错切片的用意

items[i::n] 而不是连续分块，是为了让每个线程拿到的文件大小尽量均匀。连续分块时若文件夹按名字排序、大文件恰好集中在前缀，就会出现「线程 1 跑完剩下三个还在啃同一个大 PDF」。交错之后进度条推进更平滑，停止响应也更及时。

停止语义

「停止」置位 threading.Event，worker 在每个文件开始前检查；已经写盘的文件不回滚，剩余文件标为「已取消」。关窗口时先置位再 pool.waitForDone(5000)，避免线程还没退出就析构控件导致崩溃。

06输出命名与冲突策略

这是本项目唯一一次真产品级 bug。最初把 7 个样例文件批量输出到同一目录，结果只剩 3 个文件——sample.pdf、sample.docx、sample.xlsx 的主名都是 sample，全部映射到同一个 sample.md 互相覆盖。命令行时代用户一次只转一个文件，感知不到；批量界面必然暴露。

修复方式是引入两个正交的维度，而不是简单加序号：

为什么要分两段：批内重名是逻辑问题，转换前就能全部知道，所以主线程一次性分配，天然没有竞态；磁盘上已存在同名文件是运行时状态，必须写盘前查，所以留在 worker 里按 conflict 策略处理。把两者混在一处做，就会出现「两个线程同时判断 sample.md 不存在，然后都去写」。
路径归属的另一半：target 只在真正写盘成功后才算数。「无内容」与「失败」两条分支都会把它清空，否则那一行带着一个从未创建的路径，看起来像成功、双击还会报「找不到文件」。「跳过」则保留路径——那个文件确实存在，只是这次没动它。

实测结果

7 个样例（pdf/docx/xlsx/pptx/html/csv/gbk.txt）批量输出到同一目录，修复后得到：

sample.csv.md   sample.docx.md   sample.html.md   sample.pdf.md
sample.pptx.md  sample.xlsx.md   sample_gbk.md

7 个文件全部保留，无需用户改命名方式——「自动」模式自己识别到了冲突组并切换到保留原扩展名。

密钥的三条路径

Azure 侧的密钥不进配置文件，只从环境变量读，这是 markitdown 自身的设计：

能力环境变量界面里配什么
Azure Document IntelligenceAZURE_DOCUMENT_INTELLIGENCE_KEY只填 Endpoint 与 API 版本
Azure Content UnderstandingAZURE_AI_SERVICES_KEY只填 Endpoint / Analyzer / 文件类型

一处已修正的默认值：settings.py 原本在配置文件缺失时把「记住密钥」当作 True，与文件头声明的「勾选后才落盘」矛盾——新用户第一次启用 LLM 并填了 Key，退出时就会被明文写进 %APPDATA%。现在三处默认全部改为 False，「默认值」按钮复位时也一并取消勾选。

配置的可移植性

「另存为 / 载入」导出的是同一份 JSON，可以把一套调好的参数（含 DI/CU Endpoint）拷到另一台机器直接载入；导出同样受「记住密钥」开关约束，勾选状态下导出的文件含明文 Key，跨机分发前要注意。

10.3 安装动作

  1. 把 MarkItDownGUI.zip 拷到目标机，解压到任意非系统目录，例如 D:\Tools\。
  2. 确认结构是 D:\Tools\MarkItDownGUI\MarkItDownGUI.exe 且同级有 _internal。
  3. 双击 exe。首次运行冷启动约 1～3 秒（magika 模型加载），之后同一进程内逐文件很快。

10.4 首次运行可能被拦

exe 未做代码签名。SmartScreen 会弹「Windows 已保护你的电脑」→ 点「更多信息」→「仍要运行」。如果是从网盘、IM、邮件附件下载的，Windows 会给整个压缩包打 Mark-of-the-Web：右键 zip → 属性 → 勾选「解除锁定」再解压；或只对外层的 MarkItDownGUI.exe 做同样操作。

部分杀软会把 PyInstaller 目录版报为可疑（自解压 + 内嵌解释器的通用特征）。建议连同 build.spec、源码一起交付，或申请企业白名单；长期方案是买代码签名证书。

11验证与回归

三层验证，从内到外。GUI 程序没法靠人肉点界面做回归，所以每一层都能在无操作者参与的情况下给出退出码。

脚本覆盖层检查数耗时跑什么
scripts/verify_engine.py引擎层，不起界面26约 3 秒6 种格式关键词命中、无后缀文件靠 -x 救回、-c GB18030 解码、11 条校验规则拦截、文件夹扫描计数、输出路径唯一性、3 线程批量、落盘文件数、keep_extension 命名、序号策略、跳过策略（含「跳过项只回调一次」），以及 9 项「转不出正文」用例：png 判为无内容且不落盘、gif 失败说明中文化并给出支持范围、wav 被预检拦截且耗时 < 1 秒（不空等 42 秒超时）、失败项保留原始异常信息、启用云端仍为空时提示改文案
scripts/smoke_ui.py界面层，离屏 Qt—约 2 秒重复添加去重、文件夹扫描数、非法配置被弹窗拦截、配置读写往返且未勾选时密钥被剥离，外加「无内容」行的上色 / tooltip / 统计文案，以及一条跨线程竞态回归：worker 已写「完成」后再触发 _on_item_started，状态不得被改回去。用 QT_QPA_PLATFORM=offscreen + 临时 APPDATA，不碰真实配置
scripts/verify_exe.py打包产物9约 20 秒exe 转 6 种格式 + 无后缀文件（走 --selftest 写日志再断言）、真实启动后进程存活、窗口标题正确、整包体积

为什么 windowed exe 要设计成写日志文件

console=False 的 exe 没有 stdout，print 直接丢弃，用 subprocess 抓输出会拿到空。自检因此把结果写进 <输出文件>.selftest.log，内容形如 SELFTEST_OK chars=1234 out=…，失败则写 SELFTEST_FAIL 异常类型: 消息 加完整 traceback，同时用退出码 0/1 表达结果。这样打包验证与界面行为完全解耦。

一条被删掉的路：曾加过 --uitest 想在 exe 内跑界面自检，但在 windowed 构建里挂住 180 秒且不写日志（qoffscreen.dll 确认已进包）。原因是无控制台进程的 Qt 事件循环与离屏平台组合不可靠。最终删掉该功能，改用「真实启动 + 检查窗口标题」这条稳定路径，而不是继续绕。经验：离屏验证只在开发环境（有 stdout）做，产物验证走真实启动。

视觉验证

两个布局缺陷是几何 dump 和截图发现的，逻辑测试全绿也照样存在：

  • 纵向：中央三行网格未设行拉伸，输入栏 / 分屏 / 操作栏平分高度，表格被压到 259 px。加 grid.setRowStretch(1, 1) 后表格 506 px。
  • 横向：参数面板内容需要 960 px 而视口只有 568 px，右侧整块被裁。改为下拉项显示短中文、真实值放 userData、长说明放悬停提示，配置路径从 QLabel 挪进 tooltip（Windows 长路径不可断行会把面板顶宽）。现在内容 437 px < 视口 487 px，无横向滚动条。
  • 缩放：Qt 默认按 96 DPI 渲染，在 2560×1600 / 150% 屏上整界面偏小且面板被裁。开启 AA_EnableHighDpiScaling，并把取整策略设为 PassThrough——默认策略会把 150% 进位成 200%，反而整体过大。默认窗口尺寸同时改为随屏幕工作区自适应。
截图方法：桌面区域 CopyFromScreen 会把遮挡在上面的别的窗口一起拍进来，曾据此误判。可靠做法是对目标 HWND 调 PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)，并在同进程先声明 PerMonitorV2 DPI 感知，否则拿到的是缩放后的虚拟坐标。Qt 内部还可以直接 widget.grab()，但离屏平台缺中文字体会得到空白字形，必须在真实平台插件下用。

README 两张图的来历：scripts/make_screenshot.py 真实跑完转换再 grab()，不是设计稿。第一张只喂 samples/ 里 8 个文档，得到全「完成」态；第二张在同一批后追加临时生成的 png / jpg / gif / wav，得到「无内容」与「失败」混排的形态。两张同一逻辑尺寸 1680×940（高 DPI 下抓出来是 2520×1410），跑完会删掉生成的 .md，不污染样例目录。

现象根因处理
双击无反应 / 一闪而过只拷了 exe，缺 _internal；或目标机是 32 位 / ARM确认同级存在 _internal；winver 查架构
SmartScreen 拦住未签名 + Mark-of-the-Web右键 zip → 属性 → 解除锁定；或「更多信息 → 仍要运行」
每个文件都「初始化失败：…」magika 模型未进包（自己改过 spec）恢复 collect_data_files("magika") 后重打包

拖了图片/录音，队列里没有报错但找不到 md离线提不出正文，状态是「无内容」而非「完成」——这是刻意设计，不写 0 字节文件看「说明」列的中文原因；勾选多模态 LLM 或 Azure CU 后选中这些行再点「转换队列（批量）」，重跑会带上「无内容」
底部统计里「无内容 N」不知道是什么该计数只在本轮存在无内容项时出现，含义是「转换流程走完但没有可写出的正文」运行日志末尾列出文件名（最多 5 个，超出省略号）并说明能力边界；原始异常在每行悬停提示里

停止后仍有文件写盘停止只作用于尚未开始的文件预期行为；已完成的不会回滚
界面在 4K 屏上偏小或偏大DPI 取整策略当前用 PassThrough 按真实比例；若仍不适，可在快捷方式目标后加 /DPIUNAWARE 兼容性选项试验

14.3 加一个新参数的固定顺序

  1. engine.py 的 ConvertOptions 加字段并给安全默认值——to_dict/from_dict 自动带上，配置文件向后兼容。
  2. 若影响构造：build_kwargs() 里翻译成 markitdown 关键字；若影响 convert() 调用：convert_one()。
  3. validate() 补一条拦截规则，返回问题字符串而不是抛异常。
  4. ui_main.py 面板加控件，并在 _collect_options() 与 _apply_options_to_widgets() 两处成对读写；下拉项用 _fill_combo()（短标签 + userData + tooltip），避免撑宽面板。
  5. 若是新依赖：确认 markitdown 是否惰性导入，是则加进 build.spec 的 optional_packages。
  6. 补 verify_engine.py 检查项，跑完整闭环。
两条硬约束不要破：① engine.py 里不许 import Qt；② 对 markitdown / openai / azure 的 import 必须留在函数内部惰性执行，否则界面冒烟测试会被依赖装不全拖死。
